# Scenario Example: 16x16 Game of Life on an SK6812 Panel

This note illustrates a conceptual real-world scenario for the proposed String bit API: running Conway's Game of Life on a 16x16 grid and displaying each generation on a 16x16 SK6812 (NeoPixel-class) LED panel.

- A 16x16 cell grid is exactly **256 bits = 32 bytes**, so one generation
  fits in a single `String`. The proposal's bit methods operate on that
  state natively.
- The interesting per-frame computation is **inter-frame comparison**:
  which cells just changed, how many, whether the simulation is stable or
  oscillating. Those questions are bitwise operations on the full 32-byte
  state -- `bitwise_xor`, `bit_count`, `bitwise_or` -- where the API delivers
  C-level speed in one line of Ruby.

## Scenario

```text
A 16x16 Game of Life grid. Each cell is alive (1) or dead (0):

      col 0                                                       col 15
     +---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
row 0|   |   |   | # |   |   |   |   |   |   |   |   |   |   |   |   |
row 1|   |   |   |   | # |   |   |   |   |   |   |   |   |   |   |   |
row 2|   |   | # | # | # |   |   |   |   |   |   |   |   |   |   |   |   <-- glider
row 3|   |   |   |   |   |   |   |   |   |   |   |   |   |   |   |   |
...
row15|   |   |   |   |   |   |   |   |   |   |   |   |   |   |   |   |
     +---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+

         256 cells x 1 bit  =  256 bits  =  32 bytes  =  one `String`
```

A generation step applies Conway's B3/S23 rule cell-by-cell. The *per-cell*
work is small (count 8 neighbours), but the *per-generation* work --
"compare this generation to the previous one" -- is naturally a whole-state
operation, and that is where the bit API shines.

## State representation

```text
generation: 32 bytes, packed LSB-first, row-major
   byte[0]  bit 0..7    ->  row 0, cols 0..7
   byte[1]  bit 0..7    ->  row 0, cols 8..15
   byte[2]  bit 0..7    ->  row 1, cols 0..7
   ...
   byte[31] bit 0..7    ->  row 15, cols 8..15
```

Three of them live across the main loop:

```text
prev   32 B     previous generation
curr   32 B     current generation
diff   32 B     curr XOR prev: cells that just changed
```

## Per-generation step

The rule itself is the only place that touches individual cells. Pure Ruby
or bit API, this part is the same shape -- a double loop with neighbour
lookup:

```ruby
GRID = 16

def life_step(curr)
  nxt = +"\x00".b * 32
  GRID.times do |y|
    GRID.times do |x|
      n = 0
      [-1, 0, 1].each do |dy|
        [-1, 0, 1].each do |dx|
          next if dx == 0 && dy == 0
          ny = (y + dy) % GRID
          nx = (x + dx) % GRID
          n += 1 if curr.bit_set?(ny * GRID + nx)
        end
      end
      alive = curr.bit_set?(y * GRID + x)
      if (alive && (n == 2 || n == 3)) || (!alive && n == 3)
        nxt.bit_set(y * GRID + x)
      end
    end
  end
  nxt
end
```

This part is roughly the same cost in either implementation: 256 iterations,
each doing a few bit lookups. The interesting comparison is what happens
*next*.

## Per-generation analysis: where the bit API earns its keep

After computing `curr` we want to answer three questions per generation:

1. **Which cells just changed?** -- needed to colour them in a contrasting
   tone on the panel so motion is visible.
2. **How much changed?** -- if zero, the simulation reached a still-life
   and we can sleep the LEDs. If oscillating, we may want to slow the
   frame rate down.
3. **Has it become a 2-period oscillator?** -- compare against
   *two* generations ago, not just one.

All three answers come from **one bitwise call each, on the whole 32-byte
state**:

```ruby
diff      = curr.bitwise_xor(prev)         # which cells flipped  (32 B -> 32 B)
n_changed = diff.bit_count             # how many flipped     (Integer)
period_2  = curr == prev_prev          # 2-period oscillator? (Boolean)
```

Bit-API cost on 32 bytes:

| operation                | bit API cost                                                | what it expands to in C                              |
|--------------------------|-------------------------------------------------------------|------------------------------------------------------|
| `bitwise_xor(other)`         | 4 x `uint64_t` XOR + alloc                                  | `*d++ = *a++ ^ *b++;` unrolled 4 times               |
| `bit_count`              | 4 x `__builtin_popcountll`                                  | one POPCNT instruction per 8 bytes on modern CPUs    |
| `bitwise_or!`, `bitwise_and!`    | 4 x `uint64_t` OR/AND, no alloc                             | same as XOR, in-place                                |
| `bitwise_not`                | 4 x `uint64_t` NOT + alloc                                  | trivial                                              |

For comparison, the equivalent pure Ruby code:

```ruby
# Pure Ruby bitwise_xor on 32 bytes
diff = +"\x00".b * 32
32.times { |i| diff.setbyte(i, curr.getbyte(i) ^ prev.getbyte(i)) }
#         ^ 32 bytecode-heavy iterations: getbyte, getbyte, XOR, setbyte each.

# Pure Ruby bit_count on 32 bytes
n_changed = 0
32.times do |i|
  b = diff.getbyte(i)
  8.times { |k| n_changed += 1 if (b >> k) & 1 == 1 }
end
#         ^ 32 x 8 = 256 iterations to count bits.  No popcount intrinsic.
```

The bit-API one-liners are **one C call each, working on `uint64_t` at a
time**; the pure-Ruby versions are **tens to hundreds of bytecode-heavy
loop iterations through the VM**. On PicoRuby and mruby in particular, the
ratio is brutal: PicoRuby's bytecode dispatch dominates every cycle, so
moving the whole loop into C is the difference between "smooth animation"
and "visible stutter".

## Per-frame loop with SK6812 output

Putting it together: render alive cells white, just-flipped cells green
(so the eye can track motion), and stop when the simulation is stable.

```ruby
ALIVE_COLOR    = "\xC0\xC0\xC0".b      # GRB white-ish
CHANGED_COLOR  = "\xC0\x10\x10".b      # GRB highlight: greener than red
DEAD_COLOR     = "\x00\x00\x00".b

sk_buffer  = +"\x00".b * (256 * 3)     # 768-byte SK6812 stream
prev       =  "\x00".b * 32            # previous generation
prev_prev  =  "\x00".b * 32            # two generations ago (for oscillator check)
curr       = initial_pattern.dup       # 32 bytes; e.g. a glider

loop do
  nxt  = life_step(curr)
  diff = nxt.bitwise_xor(curr)             # <<< whole-state diff, one C call
  changed = diff.bit_count             # <<< whole-state popcount, one C call

  break if changed == 0                # still life -> stable, exit

  if nxt == prev_prev
    # Period-2 oscillator detected; could slow refresh down or reset.
  end

  # Colour each LED based on (alive?, just-changed?). each_bit_offset(true)
  # walks only the set bits, so a sparse `diff` is proportionally cheaper.
  256.times { |i| sk_buffer.bytesplice(i * 3, 3, DEAD_COLOR) }
  nxt.each_bit_offset(true) do |i|
    color = diff.bit_set?(i) ? CHANGED_COLOR : ALIVE_COLOR
    sk_buffer.bytesplice(i * 3, 3, color)
  end

  sk6812.write(sk_buffer)              # one-shot DMA / RMT

  prev_prev = prev
  prev      = curr
  curr      = nxt
end
```

Notable points:

- `bitwise_xor` produces a 32-byte `String`; comparing that to `prev_prev` is
  one `String#==`, which is again a C-level word-wise compare.
- `nxt.each_bit_offset(true)` uses `__builtin_ctzll` to skip over zero runs,
  so a sparse final state (a few cells alive) costs proportionally less
  to render -- no 256-element loop.
- The dead/alive base fill could itself be a memset; the example keeps a
  straightforward loop for clarity.

## Variations made trivial by `bitwise_or` / `bitwise_and` / `bitwise_not`

These are one-line additions to the loop above:

- **Heat trail** -- accumulate every cell that has ever been alive, so the
  panel shows a fading footprint:
  ```ruby
  heat.bitwise_or!(nxt)         # cumulative OR of every generation
  ```
  Useful for showing where a glider has travelled.

- **Recently-changed window** -- accumulate the last K diffs:
  ```ruby
  window.bitwise_or!(diff)
  window.bitwise_and!(decay_mask)   # periodically clear half the bits
  ```

- **"Where it used to be alive but is now dead"** (death-trail layer):
  ```ruby
  just_died = prev.bitwise_and(nxt.bitwise_not)
  ```

- **Forbidden-zone mask** -- a region of the panel must never be live
  (for example, a "frame" of dead cells around a smaller play area):
  ```ruby
  curr.bitwise_and!(play_area_mask)
  ```

- **Cross-fade two patterns** -- blend simulation `A` and simulation `B`
  through a position-dependent mask:
  ```ruby
  composite = a_state.bitwise_and(mask).bitwise_or(b_state.bitwise_and(mask.bitwise_not))
  ```

Each of these is **one C call on 32 bytes**, regardless of where on the
panel the work falls. The pure-Ruby equivalent of every line above is a
32-iteration loop with bytecode-heavy inner work.

## SK6812 stream layout (reference)

SK6812 / WS2812 is a one-wire serial protocol. Each LED takes 24 bits in
**GRB** order. Updating LED `i` writes 3 bytes at offset `i * 3` of the
stream buffer:

```text
byte offset   0   1   2   3   4   5   ...    765 766 767
              +---+---+---+---+---+---+      +---+---+---+
              | G | R | B | G | R | B |  ... | G | R | B |
              +---+---+---+---+---+---+      +---+---+---+
              \-- LED 0  --/\-- LED 1  --/   \-- LED 255 -/
```

## Memory profile

```text
permanent (alive across frames):
  prev          32 B
  prev_prev     32 B
  curr          32 B
  sk_buffer    768 B
ephemeral (one frame):
  nxt           32 B    (becomes next `curr`)
  diff          32 B    (from bitwise_xor)
                ------
  total      ~ 928 B
```

Less than 1 KB working set, full color output, hardware-accelerated
diffing. The Pure Ruby equivalent allocates the same number of `String`s
but spends *all of them* in bytecode-heavy inner loops.

## Why this fits microcontrollers in general

The pattern this example demonstrates is broader than Life:

- The **state of a small grid / panel / sensor array is bit-sized**
  (a few tens to hundreds of bits).
- The **interesting per-tick analysis is whole-state**: "what changed?",
  "is it stable?", "is region A overlapping region B?".

The proposed bit API makes the whole-state analysis a single C call on a
`String`, instead of a Ruby loop that touches every cell. On a desktop
CRuby that ratio is "noticeable"; on PicoRuby / mruby on a microcontroller
it is "the difference between feasible and not". And because the API is
attached to `String` rather than a new container type, the same Life
implementation runs unchanged from CRuby down to PicoRuby once the methods
land in core.
